# Проверка чтения слога: контракт API

Клиент реализован в приложении. Серверный метод предстоит реализовать в
`tajweed_app_backend_dart`. До этого приложение отправляет настоящий запрос
и показывает недоступность проверки при ошибке; локального вердикта нет.

## Запрос

```http
POST /syllable?expected=%D8%A8%D9%90
Content-Type: multipart/form-data; boundary=...

audio: <файл voice.m4a>
```

- `expected` обязателен: один арабский слог с фатхой, касрой или даммой,
  например `بَ`, `بِ`, `بُ`. Это чтение согласной с краткой гласной, а не
  произнесение названия буквы. Для начальной хамзы: `أَ`, `إِ`, `أُ`.
- Клиент передаёт глиф из задания, включая огласовку; URL кодируется библиотекой.
- Единственное поле multipart — `audio`, бинарный файл с исходным именем.
  Сервер принимает AAC в контейнере m4a и PCM wav. Текущий мобильный рекордер
  пишет m4a с частотой 44 100 Гц и системными настройками каналов;
  преобразование частоты и каналов для модели выполняет сервер.
- Адрес берётся из общей настройки сервера приложения, включая адрес из меню
  отладки. Отдельного адреса для слогов нет.
- Таймаут подключения, отправки и ожидания ответа — по 15 секунд.
  Автоматических повторных отправок нет. Выход с экрана отменяет запрос;
  временный файл удаляется после завершения проверки или отмены.

## Ответ 200

`Content-Type: application/json; charset=utf-8`. Названия полей русские,
как в существующем `/letter`. Статусы — фиксированные значения
`matched`, `mismatch`, `unclear`.

| Поле | Тип | Значение |
|---|---|---|
| `ожидалось` | string | Точный глиф из запроса, без удаления знаков |
| `услышано` | string или null | Распознанный слог с огласовкой; null, если его нельзя уверенно определить |
| `статус` | string | Совпало, отличается или нельзя оценить запись |
| `буква_совпала` | boolean или null | Совпадение согласной; null при `unclear` |
| `огласовка_совпала` | boolean или null | Совпадение краткой гласной; null при `unclear` |
| `подсказка` | непустая string | Короткая помощь на русском, готовая для показа ученику |
| `запись` | object, необязательное | Качество записи по формату существующего `/letter` |

Все поля, кроме `запись`, обязательны, в том числе поля со значением null.
`запись` содержит числовые `речь_с`, `громкость_дБ`, `чистота_дБ`
и необязательное `предупреждение` (string или null).

### Правильное чтение

```json
{
  "ожидалось": "بِ",
  "услышано": "بِ",
  "статус": "matched",
  "буква_совпала": true,
  "огласовка_совпала": true,
  "подсказка": "Верно: буква ба с касрой."
}
```

### Другая огласовка

```json
{
  "ожидалось": "بِ",
  "услышано": "بَ",
  "статус": "mismatch",
  "буква_совпала": true,
  "огласовка_совпала": false,
  "подсказка": "Вы произнесли «ба». С касрой этот слог читается «би»."
}
```

Для другой согласной с верной гласной — `false / true`; для ошибки в обеих
частях — `false / false`. При `mismatch` слог `услышано` непустой,
отличается от `ожидалось`, обе проверки определены, хотя бы одна равна false.

### Запись нельзя оценить

```json
{
  "ожидалось": "بِ",
  "услышано": null,
  "статус": "unclear",
  "буква_совпала": null,
  "огласовка_совпала": null,
  "подсказка": "Голос слышно слишком тихо. Поднесите телефон ближе и повторите запись.",
  "запись": {
    "речь_с": 0.4,
    "громкость_дБ": -38.2,
    "чистота_дБ": 8.1,
    "предупреждение": "тихо"
  }
}
```

Тишина, шум, недостаточная уверенность распознавания, отдельная согласная без
гласной или название буквы вместо слога дают `unclear`, если модель не может
уверенно определить обе части. Это просьба повторить запись, без учебной оценки.
При `unclear` обе проверки всегда null. Сервер может вернуть предварительный
кандидат в `услышано`, но клиент его не показывает. Предупреждение о плохой
записи допускается только при `unclear`.

## Правила серверной проверки

- Нужна оценка **произнесённой согласной и краткой гласной**. Простое сравнение
  текста обычного распознавания речи не подходит: удаление огласовок лишает
  проверку смысла. Способ распознавания и пороги уверенности выбирает бэкенд.
- Вердикт вычисляет сервер. Клиент не выводит «верно» из процентов, ближайших
  кандидатов или собственной транслитерации.
- При `matched` обе проверки true и `услышано` точно равно `ожидалось`.
  Сервер учитывает канонически равнозначные арабские написания при распознавании,
  затем возвращает ожидаемое написание при совпадении. Хамза с касрой остаётся
  `إِ`; ни огласовку, ни хамзу нельзя отбросить.
- Если сервер вернул чужое `ожидалось`, неизвестный статус, пропущенное поле
  или противоречивый вердикт, клиент показывает ошибку сервиса, без оценки.
- Метод не загружает запись в датасет `/recordings`. Хранение записей сервером
  остаётся отдельным решением.

## Ошибки HTTP

| Код | Когда | Ответ |
|---|---|---|
| 400 | Нет `audio`, пустой файл, нет `expected` или ожидается неподдерживаемый слог | `{"ошибка":"Некорректный запрос"}` |
| 415 | Неподдерживаемый или повреждённый аудиоформат | `{"ошибка":"Не удалось прочитать аудио"}` |
| 404 | Метод ещё не реализован на выбранном сервере | Клиент сообщает, что проверка слогов пока недоступна |
| 500 / 503 | Ошибка или недоступность модели | `{"ошибка":"Проверка временно недоступна"}` |

Любая ошибка HTTP, сети или разбора ответа остаётся технической ошибкой.
Валидный аудиофайл с тишиной получает 200 / `unclear`, а не 400.

## Отладочный экран

«Отладка → Экраны курса → Чтение слога вслух». Можно выбрать букву и
огласовку. Они фиксируются с начала запуска микрофона до ответа сервера;
в этот момент переключатели недоступны. Образец звучания доступен после
полученного результата. Повторная запись начинает новую проверку.
Сам отладочный экран не пишет учебный прогресс. Та же карточка включена
в курс огласовок: результат записывается целевому знаку на ба или слогу
в режиме `saySyllable`, по частоте и правилам попыток обычного произношения.
